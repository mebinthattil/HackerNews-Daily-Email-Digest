Claude reveals ECDSA curve origins

840 points • by ahlCVA • 57 comments
Summary

Claude, an Anthropic research model, identified the provenance of the seed values used for the NIST ECDSA curves (P‑192, P‑224, P‑256, P‑384, P‑521 and several binary curves). By scanning the 20‑byte seeds for patterns matching outputs of the 1990s C library linear‑congruential generator lrand48, Claude reconstructed the generator’s internal state and determined that each seed was produced by lrand48 initialized with a Unix timestamp (or half‑timestamp for binary curves). The required number of iterations ranged from hundreds to thousands (e.g., 1842 for P‑256). This explains the seeds without invoking any secret hash or backdoor, confirming that the curves were generated from a simple, reproducible PRNG. Claude also traced the base‑point generation for six early curves to the FreeLIP/NTL random‑number generator using small integer seeds. Unexplained aspects remain: some candidate seeds were skipped, the B‑163 binary seed is still unknown, and the base points for P‑224, P‑256, P‑384, and P‑521 have not been linked to a documented process.

0/1 Knapsack Problem in PyTorch

12 points • by yu3zhou4 • 1 comments
Summary

The article explains a new PyTorch activation‑memory‑budget solver, dp_knapsack_sliding_hirschberg, which replaces the default dp_knapsack dynamic‑programming (DP) 0/1 knapsack implementation. The original solver builds a full DP table of size (items × capacity), causing high peak RAM usage and requiring back‑tracking to recover the selected items. The new solver applies two optimizations:

  • Sliding‑window trick – keeps only two rows (previous and current) of the DP table, reducing memory from O(items × capacity) to O(capacity).
  • Hirschberg divide‑and‑conquer – recursively splits the item set, computes left/right DP rows with the sliding window, combines them to locate the optimal split, and directly builds saved‑vs‑recomputable item lists, eliminating explicit back‑tracking.

These changes lower peak RAM by ~20× (e.g., handling 2000 items on a 64 GB machine versus failure at ~100 items) and yield ≈37 % runtime improvement. Solver choice guidance: use greedy_knapsack for speed, ilp_knapsack (SciPy) for fast exact solutions, dp_knapsack for default PyTorch builds, or dp_knapsack_sliding_hirschberg for memory‑constrained environments. Usage involves setting fconfig.activation_memory_budget_solver = fconfig.dp_knapsack_sliding_hirschberg.
