An implementation using Qwen‑3‑1.7B demonstrates constrained decoding: token IDs for the options are pre‑computed, logits for the final token are soft‑maxed over only those IDs, and the highest‑probability option is returned with its probability. Calibration analysis shows severe over‑confidence; confidence bins do not match observed accuracy. Temperature scaling (optimal ≈ 3.797) flattens the distribution, aligning confidence with accuracy across bins. 2D Vehicles

479 points • by Michelangelo11 • 42 comments
Summary

The prototype implements a 2‑D rigid‑body physics core extended with three simple vehicle models—Brick, Ship and Car—using a single persistent body. The physics engine updates in fixed time steps, separating input handling, force integration and Canvas rendering. Rigid‑body state includes position, velocity, angle and angular velocity; forces applied at the centre produce translation, while off‑centre forces generate torque and spin. Collision with barriers is handled by a friction‑less edge solver that restores penetration and applies a contact impulse based on point velocity.

Vehicle behaviours are layered on the core: Brick receives forces from pointer drags, Ship adds thrust at an attachment point, and Car applies engine force, steering and tyre‑resistance forces at four wheel positions. Each tyre resolves its local velocity into longitudinal and lateral components, applying proportional damping—weak for rolling, strong for sideways slip—plus steering adjustments and a hand‑brake effect that raises rear rolling resistance and reduces lateral grip. A vehicle coordinator invokes the selected dynamics object, integrates motion, transforms shape points for drawing and selects barrier contact points using mid‑edge contacts to avoid artificial spin.

How big is a Git commit?

33 points • by theanonymousone • 6 comments
Summary

A newly‑initialized repository occupies ~64 KB in .git. Adding 250 tiny files (each “foo”) and committing creates about 47 KB of Git objects, raising the .git size to ~112 KB. Changing a single file and committing again adds roughly 17 KB, bringing the total to ~130 KB. The size increase comes from new Git objects: each commit generates a commit object, one or more tree objects (for the root and affected directories), and a blob object for the modified file. These objects are stored in .git/objects as 4 KB‑sized, zlib‑compressed files; even a 3‑byte change results in several new 4 KB objects. Log files also grow modestly (≈0.1 KB). Thus, Git’s storage model inflates small edits into multiple compressed objects, explaining why a minimal change can add several kilobytes to repository size.

Retrofitting language models to operate over bytes

65 points • by theanonymousone • 7 comments
Summary

The byte‑ified model retains the overall LTLM structure (DTP, BLT, H‑Net) while operating on UTF‑8 bytes. Each byte receives an embedding from a large, sparsely‑activated table; the embedding is augmented with the longest matching subword suffix embedding to improve performance without added inference cost. A single mLSTM layer (the local encoder) contextualizes these byte embeddings, after which a non‑causal boundary predictor (using one‑byte look‑ahead) places patch boundaries during pre‑fill. Pooling selects the final byte representation of each patch as the patch embedding, which is fed unchanged into the deep global model inherited from the original subword LLM. Depooling adds the most recent patch representation to a linear projection of byte‑level encodings, and a stack of four mLSTM layers (local decoder) processes the result. The language‑model head projects the final byte vectors to next‑byte (and optional boundary) probabilities.

Byte‑ification proceeds in two stages. Stage 1 distills a subword model into the byte model by (i) training the boundary predictor to replicate subword token boundaries (>99 % accuracy), (ii) aligning pooled local‑encoder outputs with subword embeddings through L2 loss after a few frozen global layers (n≈4), and (iii) matching patch‑level likelihoods via a temperature‑scaled binary cross‑entropy loss, optionally combined with cross‑entropy. This stage requires only one forward pass through the full network and back‑propagation through the first n global layers, offering substantial efficiency before full end‑to‑end Stage 2 training. Parameter comparisons show modest differences (‑0.7 % to +4.5 %) relative to the original subword models.

Rewind also supports bookmarks, exportable run files, and example derivations (philosophers, waiter, config‑reload) that illustrate bugs and fixes.
