MRAM Basics: How Magnetic Memory Is Replacing Embedded Flash

30 points • by giuliomagnifico • 5 comments
Summary

MRAM stores bits as magnetic states in a magnetic tunnel junction (MTJ) comprising a fixed reference layer, a free layer, and a ~1 nm MgO barrier; resistance differs for parallel vs. antiparallel alignment (tunnel magnetoresistance). Reads use a sense amplifier; writes employ spin‑transfer torque (STT), driving a current that flips the free layer’s magnetization. An MRAM cell consists of one NMOS transistor and one MTJ, requiring only ~3 extra masks and integrating above transistors in planar, FD‑SOI, or FinFET CMOS processes (28 nm, 22 nm, 16 nm nodes).

Key advantages over embedded flash:
- No high‑voltage (~10 V) charge pumps; write voltage matches core logic.
- No erase step, enabling in‑place word‑level updates.
- Write latency ≈30 ns, read ≈6 ns (22 nm), versus milliseconds for flash.
- Endurance 1 M–∞ cycles (10× flash), with 10‑year retention (up to 20 years at 150 °C).

Design checks: magnetic immunity (e.g., >1 100 Oe at 25 °C), retention at maximum operating temperature, and data survival through solder‑reflow cycles. MRAM thus simplifies firmware updates and data logging, especially below 28 nm where embedded flash is impractical.

XNU Linux: Full OS X GUI Userspace on Linux

421 points • by mmastrac • 40 comments
Summary

XNU‑Linux (AFK‑surf/xnulinux) builds Apple’s open‑source XNU kernel from published sources and loads it as a loadable kernel module (xnu.ko) inside an unmodified arm64 Linux kernel. A companion module (fki.ko) implements a “foreign kernel interface” that supplies XNU with memory, CPU threads, timers, file, network and GPU services from the host Linux kernel. The hosted XNU runs macOS 27.2.1 userspace (launchd, WindowServer, Safari, etc.) directly on the same CPUs as Linux processes, without a hypervisor. GPU access is provided via a Metal‑to‑Vulkan bridge (metal2vulkan) that routes Vulkan calls through the Linux DRM stack (Virtio‑GPU Venus on Apple Silicon M1+); CPU rendering is used when no render node is present. Boot time is 31–48 s, and a 30‑minute stress test (Safari, Notes, Calculator, etc.) completes without panics. The project requires an arm64 Linux host with PAC, 4 KB pages, ≥16 GB RAM (8 GB reserved), Xcode for disk creation, and a macOS installer disk; no Apple binaries are distributed. Build and deployment are scripted (vm‑xnu‑build.sh, xnulinux‑boot.sh, install‑service.sh). Source is split by license: xnu.ko is APSL‑2.0 (MODULE_LICENSE("Proprietary")), fki.ko is GPL; all files carry SPDX identifiers.

Nospeaker ─ Make your MacBook's trackpad talk using its haptic motor

11 points • by yakkomajuri • 1 comments
Summary

nospeaker is a macOS utility that converts a Force‑Touch trackpad’s haptic motor into a sound source, enabling speech, singing, or tones without using the built‑in speakers. It drives the motor at up to 4 k Hz, creating audible vibrations that approximate vocal formants. The program relies on the private MultitouchSupport framework (functions MTActuationCreateFromDictionary and MTActuationActuate) to send custom sine‑tone patterns, bypassing the public three‑tap haptic API. Supported hardware includes MacBook Force‑Touch trackpads (2015 onward), Magic Trackpad 2, and requires macOS 12+ on Apple Silicon or macOS 13+ on Intel. Installation options are a pre‑built binary (~/.local/bin/nospeaker), a zip release, or building from source with Xcode/Command Line Tools. Usage examples: nospeaker "hello there", nospeaker --voice Daniel "hello", nospeaker --sweep 100Hz‑4kHz. Measured output spans 98 Hz‑3.95 kHz, with peak clarity around 1 kHz and loudness 16‑34 dB above ambient. The Swift code is a single file, safe within motor limits, but may break if Apple changes the private API.

Elixir HLS makes FPGA circuits from functions written in Elixir

55 points • by kristianpaul • 0 comments
Summary

Elixir HLS is a high‑level synthesis tool that transforms pure Elixir functions (marked with defhls) into FPGA RTL (SystemVerilog) while keeping the same function executable on the CPU as its specification. The compiler (mix ehls.compile) generates circuits, simulates each against the original function, and aborts on mismatches. Current capabilities include integer arithmetic, fixed‑width types (u8, s16, u32, etc.), stateful memories, tables, and bounded loops; streams, levels, and events can be composed into pipelines or instances (definstance) that run either on the FPGA or as CPU processes. The first supported target is the Sipeed Tang Primer 25K board using AtomVM, demonstrated by a complete FM‑radio demodulator circuit. Supported tooling requires Elixir ≥ 1.18, CIRCT 1.160.0 binaries (hlstool, mlir‑opt), Python 3, and Icarus Verilog for simulation. APIs expose hardware constructs such as EHLS.GPIO, EHLS.Agent, EHLS.PubSub, and EHLS.Server (GenServer‑compatible). Documentation, tests, and build tasks are provided via mix (mix test, mix docs).
