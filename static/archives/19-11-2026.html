Ruby2ßhell: Pre-authentication RCE on stock Rails

176 points • by jdns • 22 comments
Summary

Ruby2Shell (GHSA‑34m4‑m9fh‑gqp5) stems from a one‑byte heap overflow in Ruby’s handling of single‑byte encodings (ISO‑8859, Windows‑125x) that lack a capital “ß”. When upcasing “ß”, the code writes two bytes (“SS”) but only checks space for one byte (while(*pp<end && to<to_end)). The output buffer is allocated as input length + 20 bytes; each “ß” adds one extra byte, so an input containing 21 such characters overruns the buffer by one byte. The flawed loop, present since Ruby 2.4.0, is invoked by upcase, swapcase, downcase(:fold), and casecmp?; UTF‑8 strings follow a different path and are unaffected. The overflow writes a single byte—‘S’ (0x53) for upcasing or ‘s’ (0x73) for case‑folding—just beyond the buffer, allowing an attacker to control the overflow size via input length and read out‑of‑bounds data. The issue was fixed upstream in commit ruby/ruby@d582f8f.

Distributed, high-performance blob storage on SQLite

81 points • by ghostfoxgod • 14 comments
Summary

Blobasaur is a sharded, distributed blob‑storage server built in Rust that uses SQLite as its storage engine and implements the Redis protocol (including Cluster support). It replaces Zerodha’s legacy SSDB store for JSON‑encoded UI preferences ranging from a few KB to several MB, delivering single‑digit‑millisecond latency on commodity hardware. Data is partitioned across multiple SQLite files (shards) via multi‑probe consistent hashing; each shard has a dedicated writer that batches writes in a single BEGIN IMMEDIATE…COMMIT transaction, while reads use a pool of read‑only connections. Compression (zstd in production) reduces payload size ~9×, cutting page usage and improving cache efficiency. The system runs SQLite in WAL mode with PRAGMA synchronous = NORMAL, accepting relaxed durability, and optionally an async‑write mode that acknowledges writes before commit. Cluster routing splits the keyspace into 16 384 CRC16 slots, with static slot assignment and gossip‑based node discovery. Benchmarks show 16 shards increase write throughput 3.3× (median latency ≈ 2 ms) and sustain > 25 k ops s⁻¹ for 64 KB blobs. Operational learnings include enabling incremental auto‑vacuum and integrating TTL cleanup into the main writer to avoid latency spikes. Blobasaur is open‑source (AGPL‑v3) and deployed as a three‑node cluster (4 vCPU, 8 GB RAM) with p99 latencies around 2 ms.

15M web servers on one VM – smoltcp, DPDK, AF_XDP

190 points • by fessguid • 27 comments
Summary

The article outlines a proof‑of‑concept for hosting ≈15 million independent HTTP servers inside a single 10 GB VM using one CPU core.
- A naïve C server uses the five basic syscalls (socket, listen, accept, recv, send, close) and hits the 65 k port limit; extending the port range and employing multiple IPs (e.g., an IPv6 /64 subnet) can raise the address space but still falls short.
- Each kernel socket consumes ~3.3 kB, so 15 M sockets would need ~20 TB RAM, far exceeding the budget.
- The proposal replaces the kernel stack with a custom userspace runtime: guests are loaded into one process, a minimal scheduler saves only three fields (program counter, server FD, client FD) ≈ 16 B per guest, yielding ~220 MB for 15 M guests.
- Active connections (≈1 M) at ~5 kB each add ~5 GB, keeping total usage under 10 GB.
- To avoid kernel overhead, the runtime uses a user‑mode TCP/IP stack (smoltcp) with TUN/TAP, DPDK, or AF_XDP for zero‑copy I/O. Benchmarks show smoltcp uses ~620 B per idle server, DPDK the best performance, and AF_XDP close behind.
- The final architecture loads all guests, intercepts their syscalls, forwards network I/O through smoltcp adapters, and schedules execution in a tight loop, demonstrating that moving the network stack to userspace can achieve the desired scale within the memory constraints.

The flaws were independently reported by Wiz Research, Ikotas Labs, Metnir, Rapid7, and Xint, and coordinated with F5. A security release was issued on Nov 18 2026.
