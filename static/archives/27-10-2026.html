97 points • by ilreb • 20 comments
Summary

The post revisits Brooks’s Law—“adding manpower to a late software project makes it later”—and evaluates its relevance in 2026 when AI agents and large language models (LLMs) assist development. It argues that while AI eliminates some traditional bottlenecks (onboarding, meetings, breaks), the fundamental constraint remains: sequential tasks cannot be parallelised arbitrarily, illustrated by the classic “baby problem.” Overhead is transformed rather than removed; teams must still define completion criteria, review generated code, detect hallucinations, and integrate outputs, effectively managing the agents themselves. Deploying multiple autonomous agents without precise orchestration leads to redundant or conflicting changes. The author proposes an updated formulation: “Adding agents to a project with unclear requirements gets you the wrong answer faster,” emphasizing the need for clear specifications and coordinated control when leveraging AI in software projects.

New 'Circadian' Subtype of Depression Affecting 1 in 4 Patients

38 points • by gmays • 9 comments
Summary

A study of 11,380 participants from the Australian Genetics of Depression Study identified a “circadian” depression subtype affecting roughly 25 % of patients. Researchers defined this subtype by six criteria: seasonal symptom variation, delayed sleep midpoint, pronounced social jet‑lag (different sleep timing on work vs. non‑work days), evening chronotype, longer total sleep when possible, and morning fatigue. Individuals with this profile tended to develop depression earlier, exhibited more severe features (mania, psychosis, suicidality), gained weight during episodes, and showed higher genetic risk for neurodevelopmental, inflammatory, and cardiovascular disorders. They responded poorly to standard antidepressants and experienced more side effects. Overlap with atypical depression existed but many cases were distinct. The authors suggest that interventions targeting circadian regulation—such as light therapy and melatonin—may be more effective for this subgroup and should be considered early in treatment planning. The findings were published in the British Journal of Psychiatry.

Writing about pratt parsing so I remember it

25 points • by dverlaeckt80 • 1 comments
Summary

The post documents a personal experiment converting a C‑expression calculator from a shunting‑yard implementation to a Pratt parser. It notes that Pratt parsing is rarely covered in standard textbooks (e.g., The Dragon Book) and is more common in compiler‑development circles.

Key points:
- Shunting‑yard uses an explicit operator stack and binding‑power comparisons; the author provides a minimal C version that emits postfix tokens.
- Pratt parsing replaces the stack with the call stack: expr(parser, left_bp) parses a prefix token (nud) then repeatedly processes infix/postfix tokens (led) while the current token’s binding power exceeds left_bp. This mirrors stack unwinding in shunting‑yard but yields cleaner, more extensible code.
- Adding parentheses is shown by assigning a binding power of 0 to ‘(’, calling paren() to parse the enclosed sub‑expression, and checking for the matching ‘)’.
- The author highlights that each operator can have its own prefix and postfix handler, enabling straightforward extensions such as unary +/- and postfix operators.

The article concludes with references to the “Crafting Interpreters” chapter and a repository containing a more feature‑rich example.

Type Server Protocol

241 points • by adamnemecek • 26 comments
Summary

The Type Server Protocol (TSP) is a JSON‑RPC interface for Python type‑analysis servers. It builds on Language Server Protocol (LSP) data shapes (Position, Range, URI strings) and uses a “typeServer/” method prefix. Compatibility is expressed with semantic version strings; minor version changes may break, while patch changes are backward compatible within a minor line (e.g., 0.4.1). A client connects to the server via a main channel (stdio or Node IPC) and optionally opens additional read‑only IPC channels for concurrent queries. Session flow: start server, LSP initialize, call typeServer/getSupportedProtocolVersion, obtain a snapshot with typeServer/getSnapshot, issue type‑query or import‑resolution requests tied to that snapshot, and handle typeServer/snapshotChanged notifications when analysis results become stale. Snapshots are non‑negative integers that never decrease; stale‑snapshot requests must return a ServerCancelled error (‑32802). Type queries (computed, declared, expected) accept a node or declaration argument and return JSON‑serializable type objects with kind, id, and flags. Multi‑connection support is negotiated via initialize capabilities and requires a common transport (currently “ipc”). All payloads must conform to the defined shapes, and extra connections are read‑only and must reject LSP or state‑changing messages.

  • CPU emulator for 64‑bit Windows (LDT modification unavailable; NtSetInformationProcess returns error).
  • Win16‑to‑Win32 conversion routines auto‑generated from convspec (e.g., DestroyWindow16 maps to DestroyWindow via handle translation).
  • DOS emulation for Win16 programs; can set DOS version via VDMDOSVER, though functionality is limited and DOSBox/MS‑DOS Player are recommended.
  • HANDLE conversion between 16‑bit and native Windows handles.
  • Compatibility fixes for installer detection and Windows directory redirection; attempts to write %WINDIR%\*.ini are redirected to user‑writable locations.

Build instructions (Visual Studio 2017): 1. Clone repo, edit PropertySheet.props. 2. Create build directory, run cmake .. and make.
