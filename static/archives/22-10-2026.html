WorldTUI: I trained a 360M model to pretend to be a terminal

154 points • by alphax314 • 20 comments
Summary

WorldTUI is a 360 M‑parameter language model fine‑tuned to simulate a terminal by predicting screen‑grid updates from raw keypresses. Built on Qwen2.5‑Coder‑0.5B, the model was trained on 336 k synthetic sessions (≈2 B tokens) generated in Docker, with randomized prompts, sizes, and activities (bash, vim, tmux, Python, snake). Input tokens encode keystrokes and time‑waits; output tokens describe row edits, cursor moves, and copy operations, reducing full‑screen redraws from ~3 000 to a few tokens. Training incorporated DAgger‑style self‑correction: the model predicts 1‑4 steps, compares to ground truth, and learns to repair its own errors, improving PresetBench from 24/47 to 38/47. Parallel row decoding with speculative verification cut large‑frame latency from 6.7 s to 0.87 s on RTX 4090 and to ≈0.9 s in a WebGPU browser demo (int4, 208 MB). Evaluation (ShellBench, PresetBench, memory read‑back tests) shows modest command correctness and limited persistent filesystem state. The demo runs locally in Chrome/Edge; performance is slower in Firefox. Future work may explore broader application training and alternative generation methods.

OpenAI CLI

96 points • by armcat • 13 comments
Summary

The OpenAI CLI provides a command‑line interface to the OpenAI REST API. It can be installed via Homebrew (brew install openai/tools/openai) or with Go (go install github.com/openai/openai-cli/cmd/openai@latest), requiring Go 1.26+. After installation the binary resides in $HOME/go/bin or $GOPATH/bin; add this directory to PATH for command access. The CLI uses a resource‑based syntax (openai <resource> [subresource…] <command> [flags]) and supports both standard API keys (OPENAI_API_KEY) and admin keys (OPENAI_ADMIN_KEY). Global options include --api-key, --admin-api-key, --organization, --project, --base-url, --header/-H, --format, --format-error, --transform, and --debug. Tab‑completion, help (--help), and output formatting (json, jsonl, yaml, etc.) are built‑in. Image generation saves files to ~/Downloads/gpt-images/ by default; variations are created via images edit. File uploads accept plain paths; JSON/YAML arguments can reference local files with @filename, @file://, or @data://. An optional mutual‑TLS mode requires OPENAI_MTLS_CLIENT_CERT_FILE and OPENAI_MTLS_CLIENT_KEY_FILE and a custom base URL. Update checks query GitHub releases daily (disable via OPENAI_CLI_NO_UPDATE_CHECK=1). The project is Apache‑2.0 licensed and contributions follow the repository’s CONTRIBUTING.md.

Rust Style Guide

293 points • by kaycebasques • 24 comments
Summary

The Google Rust Style Guide defines consistent, tooling‑friendly conventions for Rust code used across Google projects (Android, Chromium, Fuchsia, etc.). It aligns with the official Rust style where not conflicting, emphasizing readability, long‑term maintainability, and support for large‑scale refactorings. Library code must follow binding API‑design rules; application code treats them as strong recommendations. Crates should be small, preferably one file, with a flat directory layout; leaf modules are named after their primary item, and non‑leaf modules contain only declarations and re‑exports. Glob imports are prohibited except for specific C++ interop cases; use statements must import whole modules, traits are imported locally, and top‑level functions are called with explicit module prefixes. Formatting follows rustfmt with max‑width 100, lowercase hex literals, and macro matcher formatting. Ownership guidance discourages Rc/Arc except when necessary and prefers borrowing over cloning. Function signatures favor flexible references, iterator‑based inputs/outputs, impl Into, enums over bools, and appropriate error types (Option, Result, panic!). Type design prefers newtypes, named fields, and standard‑library trait implementations; generics are favored over dyn Trait, and extension traits carry an “Ext” suffix. Important traits (Copy, Clone, Default, PartialEq/Ord, etc.) should be implemented when semantically appropriate.

Using LLM for confidence scoring is a bad idea

80 points • by jimauthors • 18 comments
Summary

LLMs generate confidence scores as plain text continuations, not as calibrated probability estimates derived from evidence. A true confidence measure must (1) reflect the amount of relevant information used for a prediction and (2) be validated against actual outcomes across many instances (calibration). Weather forecasters illustrate this: their percentages are computed from data and updated with new observations, and they are judged accurate only by comparing predicted confidence levels with observed frequencies over time. LLMs lack both properties; their token‑by‑token generation learns the form of confidence statements but not their correspondence to correctness. Consequently, LLM scores vary with phrasing, repeated queries, or preceding text, and cannot be trusted without extensive empirical validation. A reliable alternative is to build an external rule‑based confidence system: identify observable cues (e.g., source relevance, answer consistency), initialize confidence from historical success rates, record each prediction’s outcome, and iteratively adjust the rule to match observed accuracies. This approach yields consistent, calibrated confidence scores independent of the LLM’s text generation.
