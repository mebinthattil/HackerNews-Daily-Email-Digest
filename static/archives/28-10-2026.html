Git for the US Code

263 points • by alansaber • 45 comments
Summary

The article proposes a version‑controlled system for the United States Code analogous to Git, enabling users to retrieve the exact statutory text in force on any chosen date, see which public law introduced each amendment, and view effective‑date notes. It notes that the US Code is only prima facie evidence of law, with the Statutes at Large prevailing where discrepancies exist, and that amendment information is currently embedded in prose notes. A case study of 365 changes across nine titles (2017‑present) showed 361 reproduced the subsequent release point exactly, while four required partial confirmation. The system records the law and its effective date (261 by default enactment, 72 by explicit notes, 29 by amendment‑specified dates). Limitations include lack of retroactive reach‑back warnings, reliance on pattern‑based date extraction, and the need for users to consult original language for critical matters. The work builds on recent research highlighting temporal validity failures in language models and demonstrates that accurate statutory lineage is essential for reliable legal AI applications.

The resulting microscopic photograph shows ink droplets in motion as they are deposited onto paper, illustrating the interplay of fluid dynamics and printer technology.

The author created three software extensions to resolve these issues:

  • ANS MACE Fixer – patches the on‑board MACE Ethernet driver.

Installation requires an external SCSI boot volume (BlueSCSI) with Mac OS 9.1 or later, the pre‑production ROM DIMM, and optional PCI video/Ethernet cards for testing. The extensions leverage the Copland‑era native‑driver model, Name Registry, and PCI DDK tools (e.g., ROM Fiend) to register and load the drivers early in the boot process, making the ANS fully functional under both Mac OS and AIX.

Decompiling Fast Food Tycoon 2: Drawing the World

39 points • by healeycodes • 7 comments
Summary

Fast Food Tycoon 2 was reverse‑engineered with Ghidra, extracting 4,046 functions (~9.5 MB C‑like code) and indexing them in SQLite for rapid queries. Runtime memory was accessed via ReadProcessMemory to locate variables such as cash, camera position, and selected building; the game’s Windows message handler was patched to issue UI‑thread commands, and an automated UI crawler identified remaining controls.

The renderer operates on a 16‑bit color buffer with a separate lighting byte, using a dirty‑region system and multiple passes: background restoration, temporary shape marking, covering object draw, outline generation, and final fill, followed by a dithered color‑light merge. Daylight follows a 25‑value hourly table (70 → 251); lamp activation thresholds use lamp.id & 7, turning on around 18:25 and off near 05:35, with light pools clamped to ≥160. Building light masks (e.g., h_pizz_a1.m.spr) store per‑pixel brightness, combined with night window colors (h_pizz_a1.l.spr).

Animations are stored in .ani sprite sheets; each frame includes a movement vector (e.g., gehen4 (+1.25, 0)). Walker direction is derived from node deltas, with speeds ranging from 27 px/s (errand boy) to 13.8 px/s (celebrity). Indoor rendering mirrors the overworld but fixes ambient light at 248 and employs a specific draw order for furniture.

Hidden mechanics include persistent citizen schedules (e.g., Goths stay home until 09:00) and a detailed pizza‑scoring system that evaluates topping distribution across 24 regions, symmetry, ingredient compatibility, and plagiarism detection, penalising copied recipes. The game’s internal name is “Pizza3,” and decompiled fonts were reused for the article’s graphics.
