Telegram Desktop vulnerability allowed any user's file to be stolen

180 points • by g-b-r • 14 comments
Summary

Telegram Desktop processes clicked tg:// links by serialising commands (keyword;argument;) over a local socket when an instance is already running. The separator “;” is not escaped, allowing a crafted link to inject additional commands (e.g., CMD:quit). One injectable command is OPEN:, which accepts any URL scheme. Telegram also implements an internal interpret: scheme used by its release‑publish script; it reads a supplied instruction file and sends the referenced file to a specified channel without authorization checks.

An attacker can place such instruction files on the victim’s disk by sending them as automatic‑download attachments in a group, causing them to be saved in a predictable location (e.g., %APPDATA%\Telegram Desktop\Downloads). By delivering a malicious tg:// link that injects multiple OPEN:interpret: commands, the attacker triggers reading of arbitrary files (e.g., tdata/key_datas, tdata/D877F…s) and uploads them to a channel they control. The extracted key data can reconstruct the DEK and decrypt the session authorization, enabling full account takeover, especially when no local passcode is set.

Mitigations: upgrade to Telegram 7.2.9+ (removes interpret: and escapes the socket separator), enable “ask where to save each file”, restrict group invitations, and set a strong local passcode.

1234 points • by ilreb • 147 comments
Summary

The Deno team is moving to Cloudflare to combine their runtime work with Cloudflare Workers and Durable Objects. Their roadmap includes:

  • Continued support for the Deno runtime for one year, with monthly bug‑fix and security releases, after which development will cease; the runtime will remain open source.
  • Deno Deploy will operate for six months before shutdown, with migration assistance for paying customers to Cloudflare Workers.
  • The JSR package registry will stay active, transitioning its infrastructure to Cloudflare.
  • Ongoing work on the Rust‑based V8 binding (rusty_v8) and its integration into Cloudflare’s worker engine (workerd).
  • Introduction of “celld,” built on the Workers model, leveraging Durable Objects for distributed applications, providing built‑in scaling, persistent state, WebSockets, and a high‑level JavaScript API—particularly aimed at AI agent workloads.

The move prioritizes a unified platform for building servers across Cloudflare’s network or other infrastructures, ending separate Deno runtime and hosting development.

WSL3 Performance is about 5-60% faster than WSL2 depending on the workload

19 points • by tonymet • 2 comments
Summary

The benchmark compares WSL 2.6.3.0 (Linux 6.6.87.2) with WSL 3.0.2.0 (Linux 6.18.40.1) using an Alpine 3.23.0 rootfs, Go 1.27.1, and a host with an Intel i5‑8500T (2 vCPUs, 4 GB RAM allocated).

Microbenchmark results (perf bench)
- Sequential memory bandwidth ↑ 61 % (7.84 → 12.64 GB/s), driven by page_reporting.page_reporting_order=5 reducing hypervisor page‑table walks.
- Scheduler/IPC latency ↓ ≈ 11 % for sched/pipe and sched/messaging, thanks to 6.18 scheduler refinements and tighter VMBus interrupt handling.
- Basic syscall (getppid) latency ↓ 3.8 %, limited by CPU architecture.

Real‑world workload (GoReleaser build)
- Wall‑clock time improves ≈ 4 % (≈ 7.5 s).
- Kernel time (openat, newfstatat, mmap, futex) drops ~16 % (≈ 9 s saved), reflecting lower trap overhead and better slab caching.
- > 80 % of compile time remains user‑space CPU bound, constrained by the two pinned vCPUs.

Takeaways
- workloads with high IPC or memory churn (in‑memory databases, container‑dense pipelines) see sizable gains from the memory‑bandwidth and latency improvements.
- compute‑heavy builds are limited by allocated CPU resources; kernel improvements reduce sys time but overall duration stays near the hardware ceiling.

Can you use autoregressive diffusion to generate market data?

90 points • by jsomers • 11 comments
Summary

The post details a 2026 summer internship in which Kavish built an autoregressive diffusion model to generate market‑book events. Using four years of US equities data (timestamp, price, event type, etc.), the architecture combined a causally masked transformer encoder with two heads: a categorical head predicting event kind (expanded to 20 classes for trades, BBO updates, and specific discontinuities) and a diffusion head generating continuous attributes (price, elapsed time). Initial DDPM training on a 1,000‑step cosine schedule proved unstable, causing exploding trajectories; switching to flow‑matching (rectified flows) yielded stable sampling with fewer steps. To address the mixed continuous‑discrete nature of market data, Kavish introduced “atom smoothing,” smoothing spiky distributions (e.g., zero‑time gaps, penny‑size price moves) then re‑injecting point‑mass probability. Evaluation used total‑variation divergence on marginal distributions and a classifier distinguishing real versus synthetic events, showing improved realism after flow‑matching and atom smoothing. The model still degrades over long rollouts, highlighting open questions about the balance between categorical and diffusion predictions for accurate market‑data synthesis.
