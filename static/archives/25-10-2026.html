How Japanese Dried Bonito Is Made

27 points • by bookofjoe • 3 comments
Summary

Kanesa Katsuobushi Shoten, a Nishi‑Izu workshop founded in 1882 and now run by fifth‑generation craftsman Yasuhisa Serizawa, preserves the 200‑year‑old “tebiyama” hand‑fired smoke‑drying technique for katsuobushi (dried bonito). The process begins with fresh bonito filleted and boiled for 90 minutes, then smoked more than ten times over a hand‑tended wood fire. The fish is repaired with bonito paste, inoculated with koji mold for fermentation, and finally sun‑dried for several months—over half a year—until it becomes as hard as wood and acquires a jewel‑like sheen. The tebiyama method involves digging a vertical 2‑meter‑deep pit, igniting raw Izu wood (oak, sawtooth oak, cherry) at the bottom, and exposing the fish to high‑temperature open‑flame smoke. Originating in the Edo period (≈300 years ago) in West Izu’s Tago district, this method is credited with locking in intense umami and producing exceptionally rich‑flavored bonito flakes, a technique now retained by only a few Japanese manufacturers.

The Goose Programming Language

370 points • by bobbydigitales • 54 comments
Summary

Goose is a memory‑safe systems language that eliminates heap allocation, garbage collection, reference counting, and explicit lifetime annotations. All dynamic values reside on compiler‑managed data stacks; growth advances a bump pointer and memory is freed automatically at scope exit. References remain valid during stack growth, enabling stable links without reallocation. The compiler infers a static root for every reference, rejecting out‑of‑scope uses without requiring lifetime syntax. Nested structures are stored inline as contiguous metadata‑plus‑elements blocks, eliminating pointers and reducing allocation overhead. Enums can be compiled in fixed‑size (tag + largest payload) or variable‑size mode, yielding up to 4× memory savings and 2× speed improvements. Links are stored as 1‑, 2‑ or 4‑byte relative offsets, making data position‑independent and directly usable as a file format; loading validates framing, tags, lengths, and offsets. Values are constructed in place, so returning arrays or building structures incurs no copying. Errors propagate across calls via static checks instead of unwinding. Generics and higher‑order functions are monomorphized at compile time, incurring no runtime overhead. Goose compiles to a single C file, runs anywhere a C compiler is available, and includes a TinyCC backend for in‑process execution.

Small Programs and Languages

100 points • by andsoitis • 7 comments
Summary

Small programming languages are valued for minimal syntax and core concepts while retaining expressive power. Assembly is noted as extremely simple syntactically—essentially a list of opcode mnemonics—yet its ISA-specific nature limits portability. SNOBOL, though a string‑processing language, shares assembly’s jump‑only control flow. Extremely compact high‑level languages include:

  • Forth – only spaces separate tokens; highly flexible.
  • Lisp/Scheme – tiny core syntax with powerful macros.
  • Tcl – everything is a string, enabling language construction.

Lua’s 27‑page core, C’s compact yet expressive design, Zig’s C‑like size, and JavaScript’s small core (functions, arrays, objects) illustrate various trade‑offs between size and usability. David Ungar’s “simplicity trumps expressiveness” principle argues that a slightly simpler system is preferable to a complex, opaque one. “Microworlds” are self‑contained environments that benefit from concise languages, quality documentation, beginner‑friendly error messages, and well‑designed standard libraries. The Ramda functional library for JavaScript exemplifies how a small, composable library can feel like a separate language while adding expressive power.

User‑space software configures cameras, streams frames, and schedules SAD tasks to compute disparity maps.
