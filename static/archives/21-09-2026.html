Kev: Tiny Jev-like family of decision models built on top of Qwen3.5

58 points • by tosh • 14 comments
Summary

Kev is a family of compact decision‑making models built on Qwen 3.5 (and earlier Qwen 3) that support yes/no (noul), multiple‑choice (choice), and rating (score) questions in a single API call. Three model sizes are released—0.8 B, 4 B, and 9 B—each with LoRA adapters and a pointer head; the 4 B and 9 B variants run in bf16 on a 32 GB Mac, while all sizes run on CUDA. The API matches TypeSafe’s System One, enabling use of the provided Python SDK or a local HTTP endpoint. Requests encode the state text once and attach independent question blocks; isolation is enforced by attention masks (or row‑wise processing for DeltaNet layers). Training uses cross‑entropy on public datasets and generated policy examples (≈10 k decision‑v7, 1.6 k rule‑structure samples) for two epochs with rank‑16 LoRA. Benchmarks report accuracy, Brier score, and calibration across development (decision‑v7) and out‑of‑domain (transfer‑v4/v9) suites; Kev‑9B approaches Jev but shows calibration gaps on new sources. Fine‑tuning on custom JSONL data (few hundred labeled examples) is supported via --init_from to retain base knowledge. Serving on Apple Silicon is slower than on GPU; caching and optional flags (KEV_MERGE, KEV_ATTN) adjust performance. All code, weights, and licenses (Apache‑2.0) are publicly available.

AX – Google’s Open Agentic Orchestrator

480 points • by blazarquasar • 64 comments
Summary

AX is an open, declarative control plane for executing agentic workloads, originating from Google research on agentic runtime systems and large-scale compute. It targets a new computing paradigm characterized by stateful, bursty, long‑running actors that perform intensive computation for brief periods before pausing for model, tool, or human inputs. Traditional orchestrators for stateless microservices or batch jobs are inefficient for such workloads due to idle sandbox costs and lack of sub‑second suspend/resume capabilities. AX abstracts tasks, workspaces, network policies, and models into core primitives, enabling developers and researchers to manage massive fleets of agents without rebuilding infrastructure. The platform builds on Google DeepMind’s agent runtime research and leverages existing isolation, resumption, and scheduling expertise, while providing agentic abstractions and generative runtime components.

The Effect of CRTs on Pixel Art (2024)

208 points • by tobr • 19 comments
Summary

The article examines how cathode‑ray tube (CRT) displays influence the perception of pixel art and how artists compensated for hardware limits.
CRTs introduce scanlines, color‑bleeding, and slight blur, which can mask blocky edges but do not eliminate visible pixels; cheap PAL/NTSC sets produce more fuzziness than high‑quality RGB monitors.
 Early 8‑bit systems (C64, NES) were constrained to low resolutions (e.g., 160×200) and fixed 16‑color palettes, prompting programmers to employ dithering (pixel‑level patterns to simulate intermediate colors) and anti‑aliasing (intermediate‑color pixels to smooth edges).
16‑bit platforms (Amiga 500, SNES, Mega‑Drive) expanded to 32 selectable colors from larger palettes and modest resolutions (~320×240), allowing richer graphics and more extensive use of dithering/AA.
 Signal quality matters: separate RGB (SCART) yields the sharpest image; composite or RF adds additional blur and color artifacts. CGA color‑blending exploits NTSC composite artifacts to create extra colors, unrelated to the CRT itself.
Aspect‑ratio handling differs: CRTs supported non‑square pixels (e.g., 320×200 vs 640×480), while modern flat panels enforce square pixels, causing distortion when old assets are displayed 1:1.
 Modern pixel‑art creators often omit dithering/AA, resulting in overly blocky images, despite the fact that these techniques improve visual quality on any display, including CRTs.

Amiga Unix, Again

94 points • by doener • 5 comments
Summary

Amix (Amiga Unix) is a community-driven revival of Commodore’s System V Release 4 for Amiga, originally released 1990‑92 on A2500UX and A3000UX. The project provides a modernized system for 68040/68060 machines and contemporary accelerator hardware, using an open development process documented in “the grimoire.” Installation is available via bootable floppy and CD‑ROM images for real hardware, with emulation support; a classic tape installer is planned. A remote package client, apkg, accesses a hosted repository (pkg.amigaux.org) delivering GNU/BSD tools such as grep, gzip, less, patch, and zlib, and will later include X11R6.3, Mesa, and a native gcc. Current achievements include kernel ports for 68040/68060 (MMU required), Z3660 accelerator drivers (SCSI, Ethernet), Zorro III SCSI drivers, an OpenLook desktop, and a functional Quake benchmark. Ongoing work covers RTG graphics for Z3660, accelerator Ethernet throughput, read‑only CD filesystem, and installer polishing. Future goals are native gcc, full X11/Mesa stack, firmware Ethernet fixes, and a complete release of packages, source, documentation, and manuals. Development combines generative‑AI assistance for reverse‑engineering binary kernels with manual review and hardware testing.

Show HN: Mini-AGI – Dynamic continual learning model trained on 8GB VRAM

54 points • by volotat • 10 comments
Summary

mini‑AGI is a byte‑level continual‑learning language model designed to train from scratch on a single consumer GPU with ≥8 GB VRAM. Weights reside on disk and are paged into VRAM as needed, allowing the parameter count to be limited only by available storage. The architecture processes each byte through two dense prelude blocks followed by a recurrent block applied up to 24 times; each application selects its own top‑8 experts from a shared pool, with adaptive depth governed by a PonderNet‑style halting head. Trunk components (embeddings, attention, routers, halting head) run at 0.1× the expert learning rate, drastically reducing catastrophic forgetting (≤0.01 nats loss increase after 524 k characters of single‑subject training). The expert pool grows or prunes based on demand, using recombination of hidden units for new experts and retaining Adam moments per expert. Training uses batch‑1 streaming of raw bytes (256‑byte alphabet), no tokenizer, and rotary positional encodings. The model runs on an RTX 3070‑laptop GPU, occupies ~540 M parameters (≈32 experts resident at a time), and achieves ~2.4 GFLOP/byte training cost comparable to a dense 400 M byte‑level transformer.
