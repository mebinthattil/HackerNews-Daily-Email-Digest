The scourge of x86 emulation

95 points • by dagmx • 3 comments
Summary

The article explains why emulating the x86 Total‑Store‑Ordering (TSO) memory model on ARM’s weakly ordered architecture is costly. x86 guarantees that every store becomes visible before subsequent loads, while ARM only provides this when using acquire‑load and release‑store instructions. Early FEX‑Emu implementations mapped every x86 load/store to these instructions, incurring large penalties because they were not designed for high‑frequency use. Microbenchmarks show severe slowdowns on several ARM CPUs (e.g., AmpereOne, Cortex‑X4/X925, Oryon‑3) when using acquire/release semantics, especially for unaligned accesses that trigger data‑memory‑barrier (DMB) patches.

ARMv8.3 introduced the LRCPC load instruction (FEAT_LRCPC) which matches the required TSO behavior and restores near‑baseline performance for aligned accesses; however, unaligned loads still suffer due to natural‑alignment faults. Apple’s M1 implements a hardware TSO toggle, allowing regular loads/stores to behave like x86 and eliminating most alignment penalties, with only a modest overall overhead.

The FEAT_LSE2 extension relaxes alignment requirements for acquire/LRCPC/release instructions to a 16‑byte granule, offering limited benefit because x86 applications frequently cross full cache‑line boundaries. The emulator also handles split‑lock situations by patching faulting instructions to basic loads/stores wrapped with DMBs. Overall, proper hardware support (LRCPC, TSO mode) is essential for high‑performance x86 emulation on ARM.

Bend – A language that blocks AI mistakes via proof, on CPU and GPU

442 points • by nicolas-siplis • 68 comments
Summary

Bend is a programming language designed to eliminate AI‑generated errors through formal proofs and automated parallel execution. It compiles to native code, achieving near‑C performance on a single CPU core and scaling up to 100× speed on GPUs or multi‑core systems. Its type checker doubles as a proof checker (similar to Lean or Coq), verifying code changes in under a second, enabling AI agents to validate every modification. Developers declare invariants in LAWS.bend; the compiler enforces these laws so no generated code can violate them, and proofs are stored in PROOF.bend. Parallelism is implicit: code is automatically split across available cores without explicit thread or kernel management. Installation is a single script (curl -fsSL https://bend-lang.com/install.sh | sh). Recommended workflow adds Bend commands to an AGENTS.md file (e.g., bend guide, bend PROOF.bend, and parallelization hints). The language targets backend development on Linux/macOS, emphasizes bug‑free, high‑performance applications, and provides a guide, an affine dependent type theory paper (BendTT), and a parallel runtime paper (BendRT).

Pre-Greek: The lost language hidden within Ancient Greek

66 points • by axiologist • 8 comments
Summary

Ancient Greek contains roughly 1,000 lexical items that lack any Indo‑European (IE) cognate, including core terms such as λαβύρινθος, ελαία, Ἀχιλλεύς, θάλασσα, βασιλεύς, and οἶνος. Scholars attribute these to a Pre‑Greek (“Paleo‑European”) substrate spoken by the Early European Farmers before the arrival of IE speakers from the Pontic‑Caspian steppe. Because PIE had no words for many Mediterranean flora, fauna, and maritime concepts, early Greeks borrowed local names, leaving a fossil record of the earlier language. The article outlines stratification terminology: the dominant incoming language is the superstrate, the displaced one the substrate, and neighboring influences are adstrates. Identification of substrate loans relies on (1) absence of IE etymology despite extensive comparative work, (2) phonological patterns impossible under regular PIE‑Greek sound changes (e.g., initial /dn‑, /kn‑, /ps‑), and (3) parallel unattested forms in other non‑IE Mediterranean languages (e.g., Egyptian hb‑nj ‘ebony’, Hittite winija‑ ‘wine’). Examples illustrate early borrowings (olive *elaíwā, hyacinth, cypress) and later diffusion of terms such as basileús ‘king’. The substrate hypothesis thus explains the non‑IE lexical layer in Greek.

When the fractional part of a float fixes your shader

11 points • by vinhnx • 0 comments
Summary

The author created a Voronoi‑based fragment shader (Worley noise) with UV warping and palette lookup. On one Windows PC (RTX 4070, driver 595.79) the animation stuttered, while the same shader ran smoothly on Linux, macOS, mobile, and other GPUs. Debugging revealed the issue originated in the noise function’s use of fract on large‑magnitude floats. Replacing fract(x) with x‑floor(x) eliminated the stutter, suggesting a mis‑compilation. Further investigation showed the shader was executed via ANGLE, which translates GLSL to HLSL and then compiles to DirectX 11 bytecode (DXBC). Using RenderDoc, the author captured the compiled shader and compared builds with a literal multiplier of 398.0 vs 398.1. With 398.0 the optimizer (FXC, O3) collapsed the fract call, effectively truncating the value and causing discrete jumps in the Voronoi centers; a non‑integer multiplier prevented this optimization and restored smooth motion. Switching ANGLE to Vulkan (SPIR‑V) also avoided the bug. The root cause is an optimizer bug in the DirectX 11 HLSL compiler that incorrectly treats certain float literals as integer, leading to loss of fractional precision.
