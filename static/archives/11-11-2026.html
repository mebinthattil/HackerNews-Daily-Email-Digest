Protecting SSH Keys with macOS Secure Enclave

220 points • by js2 • 28 comments
Summary

The article examines protecting SSH private keys on macOS by using the built‑in Secure Enclave rather than third‑party tools. After reviewing alternatives (Secretive, YubiKey, 1Password/Bitwarden), the author attempts the native approach because it requires no extra hardware. macOS Sequoia/Tahoe supports “Secure Enclave SSH” keys: the private key is generated inside the enclave (non‑exportable) and signing operations require Touch ID. Setup involves:

  1. Creating a CryptoTokenKit identity with sc_auth create-ctk-identity -k p-256-ne -t bio.
  2. Exporting a key‑handle file via ssh-keygen -w /usr/lib/ssh-keychain.dylib -K -N "".
  3. Setting SSH_SK_PROVIDER=/usr/lib/ssh-keychain.dylib and adding the key explicitly in ~/.ssh/config.
  4. Copying the generated public key (sk-ecdsa‑sha2‑nistp256@openssh.com …) to remote authorized_keys.

The author notes three practical issues: Touch ID enrollment failures, deprecated ssh-add -K usage, and SSH not auto‑discovering the custom key name. The UI prompt (“ctccardtoken needs to authenticate…”) is considered unattractive. Since Secure Enclave keys cannot be exported, they lack backup; the author recommends keeping an additional key (e.g., YubiKey) on servers. Overall, the method offers hardware‑bound private keys and mandatory biometric approval without third‑party software, but the user experience and lack of backup are drawbacks.

Greg Kurtzer's Ginux is now a userspace kernel

77 points • by d3Xt3r • 11 comments
Summary

Ginux is a configurable userspace kernel that runs as an ordinary Linux process and mediates syscalls for isolated workloads via an explicit, version‑ed contract. Initially a Rust bootable kernel for Rocky Linux 10, development shifted to a userspace design that intercepts managed syscalls and chooses to emulate, mediate, or deny them. The current implementation includes a security‑focused x86‑64 interpreter with a balanced ptrace backend, strict instance lifecycle, digest‑pinned OCI root filesystem, immutable index, bounded overlay, and virtualized process, credential, signal, timer, and event models. It provides virtual devices, constrained views of /proc, /sys, cgroup v2, mounts, namespaces, and a host‑shared, syscall‑mediated network backend. Ginux is used for research on AI‑agent containment, allowing contracts that selectively expose time, process info, or assigned workspaces while denying unauthorized operations. Build and test workflows are driven by Makefile targets (e.g., make build, make check, make bench‑modes). The security model trusts the host kernel, hardware, Ginux binary, and operator; the ptrace backend retains host‑kernel attack surface. Ginux is research‑grade, not production‑ready, and is licensed under Apache 2.0.

A great old-timey game-programming hack (2013)

183 points • by palsecam • 22 comments
Summary

The post recounts an optimization of tile‑copying code for a side‑scroller on an 8‑bit PC using a Motorola 6809 CPU. Background tiles are 28 × 28 pixels (14 bytes per row, 4‑bit color) and must be copied into a 320 × 240 screen buffer (160 bytes per row). The naïve routine copies each row with a 7‑iteration loop, using auto‑increment addressing, costing ~157 cycles per row. Unrolling the loop removes branch overhead, reducing row time to 120 cycles (≈30 % faster). Further improvement replaces post‑increment addressing with fixed offsets, cutting the per‑row cost to 98 cycles (≈60 % faster than the original). The final hand‑crafted routine (COPYTILE2) unrolls all 7 word copies per row, advances source and destination pointers with LEAX/LEAY, and executes in 2 893 cycles for a full tile. The author also explores a “crazy” idea using the 6809’s PSHS/PULS stack instructions to move six bytes at a time, estimating ~66 cycles per row, but notes the difficulty of handling the remaining two bytes.
